🎓 دوره جامع اصطلاحات انگلیسی برنامه‌نویسان — صفر تا آماده‌ی شرکت

مخاطب: برنامه‌نویس فارسی‌زبان که انگلیسی‌اش برای داکیومنت کافیه ولی در تیم، جلسه، Code Review و مصاحبه به اصطلاح‌ها برمی‌خوره و نمی‌فهمه یا بلد نیست درست تلفظ کنه ساختار: ۱۳ فصل — مرتب‌شده بر اساس «کجا به اصطلاح برمی‌خوری»: چرخه کدنویسی، جلسه، ریویو، گیت، ارور، فرانت، بک، دواپس، معماری، چت، استخدام

🎯 چرا این دوره؟

تو کد می‌زنی، داکیومنت می‌خونی، stack trace می‌بینی — ولی توی standup فردا صبح وقتی لید می‌گه «This is a blocker, let's touch base after the sprint» و می‌خوای جواب بدی، گیر می‌کنی. مشکل تو گرامر نیست؛ اصطلاحات شغلی‌ان که توی هیچ دوره‌ی زنی teaching نمی‌شن.

این دوره: - ۲۵۰+ اصطلاح پرتکرار واقعی تیم‌های نرم‌افزاری — با تلفظ درست به فارسی (cache = «کَش» نه «کاچه»!) - معنی + جمله‌ی واقعی از محل استفاده (جلسه، چت، PR) - دیالوگ‌های واقعی تیمی + تمرین با جواب - مرتب‌شده بر اساس صحنه‌ی برخورد — نه الفبایی

🎯 هدف این فصل: قبل از حفظ‌کردن اصطلاح‌ها، سه مهارت زیربنایی: (۱) فهمیدن اصطلاح از دل جمله، (۲) تلفظ درستِ پراشتباه‌ها، (۳) الگوی compound noun ها. این فصل «دوره‌ی روش» کل دوره است.

۱.۱ — چرا انگلیسی برنامه‌نویسی «زبان جدا» است

سه ویژگی که انگلیسی فنی را از انگلیسی مدرسه جدا می‌کند:

  1. معنی متفاوت: bug = حشره نیست، باگ نرم‌افزاری است؛ commit = ارتکاب نیست، ثبت تغییرات است؛ token = سکه نیست، توکن احراز هویت است
  2. پر از metaphor ها: pipeline خط لوله، cache مخزن، deadlock بن‌بست — تصویر ذهنی داشته باش راحت‌تر می‌ماند
  3. فشرده و خلاصه‌گویی: TL;DR، LGTM، ASAP — حروف مخفف که کل جمله هستند

قاعده فهم: معنی دیکشنری را دور بریز؛ همیشه از جمله و صحنه معنی بگیر. «We need to deprecate this API» را ترجمه لغوی نمی‌فهمی؛ ولی می‌دانی این یعنی «بریم این API را بازنشسته کنیم».

۱.۲ — 🔊 تلفظ‌هایی که ایرانی‌ها غلط می‌گویند (جداول طلا)

غلط‌های کلاسیک

اصطلاح ❌ رایج بین ما ✅ درست یادآوری
cache «کا-چه» کَش مثل «cash» — نه کاچ!
agile «آگیل» اَجایل اِ-جای-ل
data «داتا» دِیتا دِی-تا
variable «وریابل» وِری-اِبل وِ-ری-اِ-بل
query «کوئری» ✅ ولی «کِری» ❌ کْوِ-ری کْوِری
async «آسی‌نیک» اِی-سینک اِی-سینک
synchronous — سینک-رو-نوس سینک همیشه
database «داتابیس» دِیتا-بِیس دیتا-بِیس
interface «اینترفیص» این-تر-فِیس فِیس مثل face
framework «فریم‌ورک» ✅ رایج و درست فِریم-ورک —
regex «رج‌کس» رِج-اِکس regular expression
char «چار» کار character → char
GUI «گوویی» گو-یی (حرف‌به‌حرف G-U-I) یا «گویی»
image «ایمج» ای-میج ایمیج
queue «کِی-یو-اِی» ✅ (حروف) یا «کیو» کیو مثل حرف Q
pseudo «پسودو» سودو P بی‌صدا
LINUX «لای-ناکس» لی-نوکس لینوس می‌گفت «لی‌نوکس»
Ubuntu «اوبنتو» ✅ اوبونتو اُ-بون-تو
Sudo «سودو» ✅ سودو مثل pseudo

قواعد کلی برای حدس زدن

  • th = تِ ساده یا ذِ (thin → تین، with → ویذ) — هرگز «ت-ه» دوحرفی نگو
  • ed آخر فعل = فقط «د» یا «ت» (deployed → دی-پلوید، shipped → شیت) — «اِد» جدا نگو
  • تأکید compound noun روی کلمه اول: database، framework، feature branch — تلفظ دومی را ضعیف بگو
  • مخفف‌ها دو دسته: حرف‌به‌حرف (API، CSS، SQL، UI) یا کلمه‌خوانی (GUI، npm خوانده نمی‌شود!)
  • وقتی مطمئن نیستی، ساده‌ترین تلفظ آهنی-لینگویی را بگو؛ غلط گفتن رخ نمی‌دهد، نگفتن رخ می‌دهد

۱.۳ — الگوی طلایی: Compound Nouns

اصطلاحات فنی اکثراً دو-سه کلمه چسبیده‌ان. الگوی ساخت‌شان را یاد بگیری، معنی‌شان را حدس می‌زنی:

الگو مثال معنی حدس‌زدنی
اسم + اسم merge conflict تعارضِ ادغام
صفت + اسم breaking change تغییرِ شکست‌دهنده
فعل-ing + اسم coding standard استانداردِ کدنویسی
اسم + of + اسم point of failure نقطه‌ی خرابی
فعل + قید roll back برگرداندن به عقب

و فعل‌سازی: هر اسمی می‌تواند فعل شود! ship it (= منتشرش کن)، google it، we'll refactor this later — «اسکوپ شد» را هم توی تیم‌ها می‌گویی، آن‌ها هم همین کار را می‌کنند.

۱.۴ — جمله‌خوانی: تکنیک ۳-ثانیه‌ای

وقتی اصطلاح ناشناس دیدی:

1. آیا مخفف است؟ (حروف بزرگ؟) → فصل ۱۱ این دوره / جستجوی سریع
2. آیا compound است؟ (دو کلمه چسبیده؟) → الگوی ۱.۳ را باز کن
3. آیا در جمله «نقش» دارد؟ (فعل است؟ اسم است؟ صفت؟)
4. حدس بزن → در جمله بعدی تستش کن → اگر جور درآمد، یاد گرفتی

مثال: «The build is flaky» → build ساخت است، flaky شکستنی/بی‌ثبات → «بی‌یلدِ build ما بی‌ثباته» ✅

✅ جمع‌بندی فصل

  • معنی از صحنه بگیر، نه دیکشنری؛ اصطلاح‌های فنی metaphor و فشرده‌اند
  • جدول غلط‌های کلاسیک را مرور کن: cache/کَش، agile/اَجایل، char/کار
  • compound noun: تأکید روی کلمه اول؛ معنی از ترکیب حدس زدنی است
  • اسم‌سازی از هر لغت مجاز است — ship it!
  • تکنیک ۳ ثانیه: مخفف؟ compound؟ نقش دستوری؟ حدس؟

📝 تمرین فصل ۱

  1. تلفظ درست را انتخاب کن: (الف) cache: کاچه / کَش (ب) agile: آگیل / اَجایل (ج) query: کوئری / کِری (د) async: آسی‌نیک / اِی-سینک
  2. معنی این compound ها را حدس بزن (بدون جستجو): memory leak، pain point، time box، quick win
  3. جمله را به فارسی روان ترجمه کن: «Let's not reinvent the wheel — we'll just use an off-the-shelf solution for now.»
  4. سه اصطلاح که تا حالا تلفظش را غلط می‌گفتی بنویس و تلفظ درستش را یادداشت کن.
جواب‌ها
  1. (الف) کَش — (ب) اَجایل — (ج) کوئری درست است، «کِری» غلط — (د) اِی-سینک
  2. memory leak = نشت حافظه (حافظه‌ای که آزاد نمی‌شود و به مرور می‌سوزد)؛ pain point = نقطه درد (مشکل اصلی کاربر/تیم)؛ time box = زمان‌بندی محدود (برای این کار فقط X ساعت داریم)؛ quick win = برنده‌ی سریع (کار کوچک با نتیجه فوری)
  3. «چرخ را دوباره اختراع نکنیم — فعلاً از یک راه‌حل آماده استفاده می‌کنیم.» (reinvent the wheel = ساختن دوباره چیزی که هست؛ off-the-shelf = آماده/خریدنی)

فصل ۲ — چرخه کدنویسی روزمره: از feature تا silver bullet

🎯 صحنه: روز کاری معمولی — «این feature رو بگیر، این bug رو fix کن، ولی حواست به technical debt باشه». پرکاربردترین ~۲۰ اصطلاحی که هر روز می‌شنوی.

۲.۱ — هسته کار: bug، feature، fix

اصطلاح تلفظ معنی جمله واقعی
feature فی-چِر قابلیت جدید «This feature ships next sprint.»
bug باگ خطای نرم‌افزار «There's a nasty bug in checkout.»
fix فیکس رفع باگ «Hotfix is deployed.»
issue ایشو مسئله/گزارش (در tracker) «Open an issue, please.»
reproduce / repro ری-پرو-دیوس / ریپرو بازتولید خطا «I can't reproduce it on my machine.»
root cause روت کاز ریشه اصلی مشکل «We found the root cause — it's a race condition.»
workaround ورک-ا-راوند راه‌حل موقتی «It's a workaround, not a real fix.»
patch پَچ وصله کوچک «Security patch coming today.»

🔑 جمله‌ی طلایی که در هر تیم می‌شنوی: «Works on my machine!» — شوخی معروف وقتی باگی فقط روی سیستم یک نفر است. و جواب استانداردش: «Then it's an environment issue.»

۲.۲ — کیفیت و بزرگی: edge case تا spaghetti

اصطلاح تلفظ معنی صحنه
edge case اِج کِیس حالت مرزی/نادر «What about edge cases — empty cart? null user?»
corner case کورنر کِیس حالت خیلی حاشیه‌ای «That's an extreme corner case, skip it for now.»
happy path ها-پی پَث مسیر بدون خطا «The happy path works; errors are a mess.»
smoke test اسموک تست تست اولیه دود (کار می‌کند یا نه؟) «Run a smoke test before pushing.»
technical debt تِک-نیکل دِت بدهی فنی (کد سریعِ کثیف) «We're accumulating technical debt.»
refactor ری-فَک-تِر بازسازی بدون تغییر رفتار «Refactor now or cry later.»
legacy لِگِسی قدیمی و موروثی «Nobody touches that legacy module.»
spaghetti code اسپاگِتی کُد کد درهم‌وبرهم «That file is spaghetti code.»
hardcoded هارد-کُدِد ثابت‌نویسی در کد «The API URL is hardcoded — bad.»
scalable اسکِیل-ابل مقیاس‌پذیر «This design isn't scalable.»
robust رو-بَست مقاوم/محکم «Make it robust against bad input.»
flaky فلِی-کی بی‌ثبات (گاهی پاس، گاهی fail) «These tests are flaky.»

🔑 تصویر ذهنی‌ها: technical debt = وام گرفتن زمان از آینده (سریع کد بزن، بعداً بهره‌اش رو پرداخت کن)؛ edge case = لبه‌ی صندلی که کاربر می‌افته؛ happy path = جاده‌ی صاف بدون چاله.

۲.۳ — چرخه انتشار: MVP تا deprecate

اصطلاح تلفظ معنی صحنه
MVP اِم-وی-پی Minimum Viable Product — کمینه‌ی قابل‌عرضه «Ship the MVP first.»
ship / ship it شیپ منتشر کن! «Ship it! 🚀»
release ری-لیس انتشار نسخه «Release 2.0 is out.»
breaking change بریکینگ چِینج تغییر شکست‌دهنده (نسخه قبلی‌ها را می‌شکند) «This is a breaking change — major bump.»
deprecated دِپ-ری-کِی-تِد منسوخ‌شده (هنوز کار می‌کند، ولی نرو سمتش) «This method is deprecated.»
sunset سان-سِت تعطیلی تدریجی محصول/قابلیت «We're sunsetting the old dashboard.»
out of scope آوت اِو اسکوپ خارج از دامنه پروژه «That's out of scope for this sprint.»
scope creep اسکوپ کریپ خزیدنِ دامنه (کارِ اضافه‌ی ناخواسته) «Beware of scope creep.»
quick win کوئیک وین دستاورد سریع «Let's grab some quick wins first.»
low-hanging fruit لو-هَنگینگ فروت میوه‌ی آسان (کار آسانِ پربازده) «Fix the low-hanging fruit first.»
silver bullet سیل-وِر بولِت راه‌حل جادویی (که وجود ندارد!) «There's no silver bullet for performance.»
bikeshedding بایک-شِدینگ بحث بی‌مورد روی جزئیات «This is bikeshedding — move on.»

🔑 دیالوگ واقعی جلسه (فهم کن، بعد بلند بخوان):

PM:  We need payments by Friday.
Dev: Full payments are out of scope for Friday. The MVP is a
     manual invoice flow; proper integration is next sprint.
PM:  That's a hard blocker for the launch...
Dev: We can ship a quick win: Zarinpal-only, no refunds. The rest
     is technical debt we'll pay down later.
PM:  Deal. But no scope creep!

ترجمه روان: مدیر محصول پرداخت تا جمعه می‌خواهد؛ دولوپر می‌گوید پرداخت کامل خارج از دامنه است، MVP فاکتور دستی است؛ بعد راه‌حل میان‌برِ زرین‌پال‌فقط را می‌گذارد و بقیه را بدهی فنی می‌کند.

✅ جمع‌بندی فصل

  • هسته: feature/bug/fix/issue/reproduce/root cause — «works on my machine» شوخی رایج
  • کیفیت: edge case، happy path، technical debt، refactor، legacy، flaky
  • انتشار: MVP، ship it، breaking change، deprecated، sunset
  • مدیریت دامنه: out of scope، scope creep، quick win، low-hanging fruit
  • جادو وجود ندارد: no silver bullet؛ جزئیات‌بازی = bikeshedding

📝 تمرین فصل ۲

  1. درک: «I hacked together a workaround, but it's accumulating technical debt.» یعنی چه؟
  2. چه اصطلاحی مناسب‌تر است؟ «The user typed 5000 chars in the name field and the app crashed» → این یک ... است. (bug عادی / edge case / breaking change)
  3. تلفظ‌ها را بنویس: deprecate، scalable، robust، legacy
  4. حالت‌سازی: لیدت می‌گوید «Can you ship the search feature by Wednesday?» ولی می‌دانی Wednesday عدد واقعی نیست. با سه اصطلاح از این فصل جواب حرفه‌ای بده (انگلیسی + ترجمه).
  5. تشخیص: کدام‌یک technical debt است؟ (الف) تست خودکار نوشتن (ب) برای سرعت، validation را skip کردن با توضیح TODO (ج) مستندسازی
جواب‌ها
  1. «یک راه‌حل موقتی سریع‌وساخت درآوردم، ولی داره بدهی فنی جمع می‌کنه» — یعنی الان کار می‌کند ولی بعداً باید درستش کنی.
  2. edge case — ورودی نادر/مرزی که مسیر عادی را می‌شکند.
  3. دِپ-ری-کِی-تِد / اسکِیل-ابل / رو-بَست / لِگِسی
  4. نمونه: «Full search is out of scope by Wednesday, but I can ship a quick win — a basic title-only search. The advanced filters are next sprint; anything more would be scope creep.» (ترجمه: جستجوی کامل تا سه‌شنبه خارج از دامنه است، ولی یک برنده‌ی سریع — جستجوی ساده عنوان — می‌توانم بدهم؛ فیلترهای پیشرفته اسپرینت بعدی است؛ بیشتر از این scope creep می‌شود.)
  5. (ب) — skip کردن با TODO یعنی «سریع الان، پرداخت بعداً» = دقیقاً بدهی فنی.

فصل ۳ — جلسات و Scrum: ادبیات standup و اسپرینت

🎯 صحنه: ۹ صبح standup داری؛ لید می‌پرسد «Any blockers?» و تو باید در ۳۰ ثانیه گزارش بدهی. اصطلاحات Scrum و ادبیات جلسات — پرتکرارترین مکالمه شغلی تو از فردا.

۳.۱ — لغت‌نامه Scrum (چارچوب چرخه کار)

اصطلاح تلفظ معنی جمله

backlog بَک-لاگ لیست کل کارهای باقی «Add it to the backlog.»

۳.۲ — سه جمله‌ی standup (قالب آماده — حفظ کن!)

فرمت استاندارد: «دیروز / امروز / موانع»

   (دیروز اندپوینت لاگین را تمام کردم و validation را شروع کردم)

واژه‌های ریز این گزارش:

اصطلاح معنی مثال
blocker / blocked on مانع / قفل‌شده روی «I'm blocked on design approval.»
in progress در حال انجام «The PR is in progress.»
WIP work in progress — همان in progress «It's WIP, don't review yet.»
wrap up جمع‌بندی/تمام کردن «Wrapping up the payment flow today.»

ETA estimated time of arrival — زمان تخمینی اتمام «ETA? — End of tomorrow.»

۳.۳ — اصطلاحات «ادبیات جلسه» (سؤال‌برانگیزترین‌ها)

اصطلاح تلفظ یعنی واقعاً چی مثال
touch base تاچ بِیس هم‌حرف زدن سریع «Let's touch base after the demo.»
circle back سرکل بَک بعداً برگردیم سرش «Good point — let's circle back on pricing.»
deep dive دیپ دایو بررسی عمیق «We need a deep dive on the perf issue.»
take this offline تیک دیس آف-لاین این را خارج از جلسه حل کنیم «Let's take this offline — it's blocking everyone.»
action item اَکشن آی-تم کار مشخص خروجی جلسه «Action items: Ali fixes the build.»
bandwidth بَند-ویذ ظرفیت/وقت خالی «I don't have the bandwidth this week.»
heads-up هِدز-آپ خبر مقدماتی «Heads-up: deploy tonight.»
on my plate آن مای پِی-ت روی میزم است (بار کاری) «I have a lot on my plate.»
double-click on دابل-کلیک اون بازش کنیم بیشتر (تینکریلی!) «Let's double-click on that idea.»
park it پارک ایت بذاریم کنار فعلاً «Park it in the backlog.»
make the call میک ذِ کال تصمیم نهایی بگیرد «The lead will make the call.»
sanity check سَن-یتی چِک چک عقلانی/سریع «Quick sanity check before we commit.»

⚠️ این‌ها «corporate speak» انگلیسی‌اند — پر از metaphor. «Bandwidth» یعنی اینترنت نیست؛ «double-click» ربطی به موس ندارد؛ «take it offline» یعنی جلسه را رها نکنیم، بعداً خصوصی.

۳.۴ — خواستن/پیشنهاد دادن مؤدبانه (برای غریبه‌های انگلیسی!)

پیشنهاد:  How about we split the ticket?          (چطوره تیکت رو بشکنیم؟)
          Maybe we could start with the API first. (شاید اول API رو شروع کنیم)
درخواست:  Could you take a look at my PR?          (می‌شه به PR من نگاه کنی؟)
          Would it be possible to extend the deadline? (ممکنه ددلاین تمدید شه؟)
مخالفت:   I see your point, but there's a risk with... (حرفت درسته، ولی یه ریسک...)
          Not sure about that — what if the API fails? (مطمئن نیستم — اگه API فیل شه چطور؟)
بی‌اطلاع: I'll get back to you on that.             (جوابشو بهت می‌دم)
          I need to check with the team first.       (اول باید با تیم چک کنم)

✅ جمع‌بندی فصل

  • چرخه: sprint → backlog → standup (دیروز/امروز/blockers) → demo → retro
  • گزارش standup با سه قالب آماده + blocker/in progress/WIP
  • corporate speak: touch base، circle back، bandwidth، heads-up، on my plate
  • مؤدبانه: How about / Could you / I see your point, but / I'll get back to you

📝 تمرین فصل ۳

  1. درک: «Let's park it and circle back in the retro.» یعنی چی؟
  2. standup سه‌خطی خودت را به انگلیسی بنویس (کار واقعی امروزت!) — با سه اصطلاح از این فصل.
  3. حالت‌سازی: PM وسط standup می‌گوید «We also need dark mode this sprint.» تو با two اصطلاح (bandwidth، out of scope یا backlog) جواب بده.
  4. کدام‌یک corporate speak است و یعنی چی: (الف) deep dive (ب) sanity check (ج) touch base (د) low-hanging fruit
  5. تلفظ‌ها: retrospective، assignee، velocity، ETA
جواب‌ها
  1. «بذاریمش کنار و توی جلسه retro دوباره بریم سراغش.»

  2. نمونه: «Yesterday I finished the header component and started the cart logic. Today I'll wrap up the cart and push a draft PR. No blockers, but I need a design review — heads-up!»

  3. نمونه: «I hear you, but my bandwidth is full with checkout this sprint — and dark mode is out of scope for the current sprint goal. Can we park it in the backlog for next sprint's refinement?» (می‌شنوم، ولی ظرفیت من این اسپرینت پر از checkout است — و dark mode خارج از دامنه هدف اسپرینت فعلی است؛ می‌شود در backlog برای refinement بعدی پارکش کنیم؟)

  4. همه corporate speak اند! (الف) بررسی عمیق — (ب) چک عقلانی سریع — (ج) هم‌حرفی سریع — (د) کار آسان پربازده (فصل ۲).
  5. رِت-رو-اس-پِک-تیو / اِسای-نی / وِ-لا-سی-تی / اِی-تی-اِی (حرف‌به‌حرف)

فصل ۴ — Code Review و Pull Request: ادبیات دروازه کیفیت

🎯 صحنه: PR زدی؛ کامنت‌ها داره میان: «LGTM 🎉»، «nit: rename this variable»، «Blocking: this leaks the API key». ادبیات ریویو — هم خواندن و هم نوشتن.

۴.۱ — چرخه PR و وضعیت‌هایش

اصطلاح تلفظ معنی جمله
PR (Pull Request) / MR پی-آر / اِم-آر درخواست ادغام (MR = اصطلاح گیت‌لب) «Open a PR when ready.»
draft PR / WIP درَفت PR ناتمام — هنوز ریویو نخواه «It's a draft PR, still WIP.»
open a PR — باز کردن PR «I'll open a PR today.»
review ری-ویو بازبینی «PR needs review.»
approve اِپ-روو تأیید «It's approved — merge it.»
request changes ری-کوِست چِینجس درخواست اصلاح قبل merge «He requested changes.»
address feedback اَدرس فی-دبک رسیدگی به کامنت‌های ریویو «I addressed all the feedback.»
merge مرج ادغام به شاخه اصلی «Merged and deployed.»
squash اسکواش له‌کردن کامیت‌ها به یک کامیت «Squash and merge, please.»
rebase ری-بِیس بازپایه‌گذاری روی شاخه جدید «Rebase on main first.»
conflict کان-فلیکت تعارض ادغام «Fix the conflicts and re-request review.»
re-request review — دوباره درخواست ریویو بعد اصلاح «Re-requested review after fixes.»

۴.۲ — ادبیات کامنت‌های ریویو (هر کامنت یک وزن دارد ⭐)

اصطلاح یعنی وزن
LGTM (Looks Good To Me) از نظر من خوبه — تأیید تأیید نهایی
nit / nitpick نیت‌پیک — ایراد جزئی (سلیقه‌ای) غیرالزامی
blocking مانع — باید قبل merge اصلاح شود الزامی
non-blocking غیرمانع — بعداً هم می‌شود پیشنهاد
suggestion پیشنهاد آماده اعمال (دکمه apply دارد) سریع
question سوال — توضیح بده گفتگو
FYI برای اطلاعت اطلاع
TODO کار باقی‌مانده در کد یادآور
scope creep! این خارج از دامنه PR است اخلاق ریویو

🔑 چطوری بخوانی‌شان (چیزی که فقط با تجربه فهمیده می‌شود): «nit:» یعنی اعصابم خرد نشده، فقط نظر سلیقه — نگران نشو. «Blocking:» یعنی merge نکن تا اصلاح شه. بدون پیشوند ولی لحن سوال = گفتگو؛ با «please» = مودبانه الزامی.

۴.۳ — چطوری بنویسی (نه فقط بخوانی) — توضیحات PR

قالب توضیحات PR (همان که در دوره گیت دیدی، با اصطلاحات کامل‌شده):

## What
Adds password reset flow (emails + token validation).

## Why
Closes #231 — users can't recover accounts.

## How
- New endpoint /auth/reset (rate-limited)
- Reuses the email template service

## Testing
- Unit tests for token expiry ✅
- Manual test on staging ✅

## Risk
Touches auth middleware — @sara please double-check.

اصطلاح‌های این قالب: closes #231 (تیکِت خودکار بسته می‌شود)، rate-limited (محدود به تعداد درخواست)، on staging (روی محیط آزمایشی — فصل ۹).

۴.۴ — ریویو دادن با ادبیات درست

✅ سخت روی کد، مهربان با آدم:
"Nice use of a lookup table here! 🎉"
"nit: `usr` → `user` for readability? (non-blocking)"
"Question: what happens if the API returns an empty array?"
"Blocking: this logs the raw token — please mask it."
"FYI: we have a shared util for this — `formatDate()`."

❌ هرگز:
"This is wrong."              ← بدون توضیح
"Why did you do it this way??" ← لحن بازخواست
"LGTM" بدون خواندن             ← خیانت به تیم

و جواب دادن به ریویو:

"Good catch — fixed in 8f3a2b1."      (نکته خوبی بود — اصلاح شد)
"Fair point. I kept it as-is because... (توضیح) — happy to change if you prefer."
"Done ✅" / "Addressed in the latest commit."
"Not sure I follow — could you elaborate?"   (نفهمیدم — بیشتر توضیح می‌دی؟)

(Good catch = پرکاربردترین تشکر ریویو؛ elaborate = بازتر توضیح بده.)

✅ جمع‌بندی فصل

  • چرخه: draft → open → review → (address feedback → re-request) → approve → squash merge
  • وزن کامنت‌ها: LGTM تأیید / nit سلیقه / blocking الزامی / non-blocking پیشنهاد
  • توضیحات PR: What/Why/How/Testing/Risk + Closes #231
  • دادن ریویو: تعریف کن، nit را برچسب بزن، blocking را شفاف؛ جواب دادن: Good catch / Addressed

📝 تمرین فصل ۴

  1. درک: کامنت «nit: use early return here (non-blocking)» یعنی چه؟ باید قبل merge اصلاحش کنی؟
  2. حالت‌سازی: ریویوچی گفته «Blocking: no error handling on the fetch». جواب حرفه‌ای + کار بعدی‌ات را بنویس.
  3. ترجمه مفهومی جمله لیدت: «Squash it and I'll approve — but address the nits first.»
  4. کدام‌یک blocking است؟ (الف) variable name کوتاه (ب) API key هاردکد شده (ج) کامنت بدون نقطه
  5. یک PR واقعی از پروژه‌ات باز کن و توضیحاتش را با قالب فصل ۴ بنویس (What/Why/How/Testing/Risk).
جواب‌ها
  1. «اینجا return زودهنگام استفاده کن (ایراد جزئی، غیرالزامی)» — نه، قبل merge لازم نیست؛ ولی چون ارزان است معمولاً همان‌جا اعمالش می‌کنیم و Resolve می‌زنیم.
  2. «Good catch! Added try/catch with a user-facing error message and a retry — addressed in commit a1b2c3d. Ready for re-review.» (و در PR، دوباره Re-request review.)
  3. «کامیت‌ها را له کن (squash merge) تا approve کنم — ولی اول نیت‌ها (ایرادهای جزئی) را اصلاح کن.»
  4. فقط (ب) blocking است — راز لو رفته = امنیت. (الف) nit، (ج) بی‌اهمیت.

فصل ۵ — Git و ورژن کنترل: ادبیات دستورات و مکالمات

🎯 صحنه: همکارت می‌گوید «I rebased on main, force-pushed, now your branch has conflicts — cherry-pick the hotfix first.» از دوره Git دستورات را بلدی؛ الان ادبیات مکالمه‌ای را می‌گیری.

۵.۱ — اصطلاحات شاخه و همگام‌سازی

اصطلاح یعنی در مکالمه جمله واقعی

cut a branch (همان) شاخه ساختن «I cut a branch from develop.»
up to date به‌روز با ریموت «My fork is up to date.»
out of sync ناهماهنگ با ریموت «Your branch is out of sync with main.»
pull in changes تغییرات را کشیدن «Pull in the latest changes first.»
rebase on top of ری‌بیس روی «Rebase on top of main.»
fast-forward ادغام خطی بدون کامیت merge «The merge will fast-forward.»
diverged دو شاخه از هم جدا افتاده‌اند «Our branches have diverged — merge or rebase?»
stale قدیمی/متروک‌شده «This PR is stale — close it?»

۵.۲ — دردسرها و اصطلاحات نجات

اصطلاح یعنی جمله واقعی
detached HEAD سرگردانی روی کامیت (نه شاخه) «You're in detached HEAD — create a branch!»
lost commits کامیت‌های «گم‌شده» «Don't panic — reflog finds lost commits.»
dirty working tree تغییرات ذخیره‌نشده «Stash your dirty tree first.»
stash انبار موقت تغییرات «Stash, pull, pop.»
hotfix فیکس اضطراری روی پروداکشن «Cut a hotfix branch now.»
squash the WIP commits تمیزکردن کامیت‌های زشت «Squash your WIP commits before the PR.»
conflict resolution حل تعارض «The conflict resolution is trivial — take ours.»
take ours / take theirs نسخه من / نسخه او را نگه دار «Resolve with ours for now.»
green build / red build بیلد موفق / شکست‌خورده «Keep the build green.»
break the build شکستن بیلد برای همه «Who broke the build?! 😅»

🔑 مکالمه واقعی نجات (بخوان و ترجمه کن):

Dev:  Help! I did a hard reset and lost three commits.
Lead: Don't panic — check the reflog. Nothing is truly lost for 90 days.
Dev:  Found them. Now what?
Lead: Create a branch from that commit and cherry-pick onto your PR.

ترجمه روان: «ریست سخت زدم و سه کامیت گم شد!» → «پنیک نکن — reflog را چک کن؛ ۹۰ روز هیچی واقعاً گم نمی‌شه» → «پیدا شد» → «از اون کامیت شاخه بساز و cherry-pick کن روی PR‌ت.»

جواب‌ها

جواب‌ها
  1. Authentication = «تو کی هستی؟» (لاگین/توکن)؛ Authorization = «اجازه این کار را داری؟» (ادمین بودن برای حذف). می‌توانی authN شده باشی ولی authZ نشده باشی.
  2. درخواست: دروازه پرداخت برای یک تراکنش، دوبار webhook می‌زند → چون handler idempotent نیست، دوبار شارژ! علاج: idempotency key (ذخیره پردازش‌شده‌ها و رد تکراری‌ها).
  3. یعنی به جای skip/take صفحه‌بندی با offset (که در داده بزرگ کند و جابه‌جا می‌شود)، با cursor (موقعیت آخرین آیتم) ادامه بده — برای فیدها و داده حجیم پایدارتر است.
  4. «روی ایمیل قید یکتا بگذار، جدول مرجع وضعیت‌ها را با داده اولیه پر کن، و انتقال را داخل یک تراکنش بپیچ.»
  5. (ب) — PUT با داده کامل: تکرارش همان نتیجه را می‌دهد. (الف) هر بار سفارش جدید؛ (ج) ایمیل تکراری می‌فرستد (مگر با کلید ضدتکرار).

💡 p95 یعنی: ۹۵٪ درخواست‌ها سریع‌تر از این بودند — بهانه‌ای که میانگین (average) گول‌زننده است و صدک‌ها واقعیت را می‌گویند.

✅ جمع‌بندی فصل

  • محیط‌ها: local → dev → staging/QA → prod (+canary)
  • استقرار: deploy → feature flag → roll out/roll back؛ zero downtime با blue-green
  • حادثه: sev1 → mitigation → RCA → blameless postmortem؛ SPOF را پیدا کن
  • CI/CD: pipeline سبز؛ flaky test دشمن اعتماد؛ p95 > average

📝 تمرین فصل ۹

  1. فرق staging و prod و چرا روی prod تست نمی‌کنیم؟
  2. درک: «Sev1: checkout outage. Mitigation: feature flag off. Postmortem tomorrow — blameless.» سه جمله را ترجمه مفهومی کن.
  3. حالت‌سازی: دیپلویت را دیروز منتشر کردی، ارور ۵۰۰ هزارتایی امروز. با ۳ اصطلاح (rollback، feature flag، RCA) نقشه نجات بنویس (انگلیسی).
  4. چرا flaky test از باگ بدتر است؟ (به CI فکر کن)
  5. معنی: p95 latency = 2s، average = 200ms. چه چیزی را نشان می‌دهد که average پنهان می‌کند؟
جواب‌ها
  1. staging = کپی شبیه‌سازی‌شده prod با داده تستی — جایی برای شکستن امن؛ prod = داده واقعی کاربران و پول واقعی. تست روی prod = ریسک مستقیم درآمد و اعتبار.
  2. «حادثه سطح ۱: چک‌اوت از کار افتاده. کاهش اثر: قابلیت را با feature flag خاموش کردیم. جلسه postmortem فردا — بی‌سرزنش.»
  3. نمونه: «Rolling back to the last known-good release now. Long-term fix goes behind a feature flag. I'll start the RCA doc — root cause looks like a missing env var.»
  4. چون اعتماد به CI را می‌کشد: بقیه‌ی تست‌ها را بی‌اعتبار نشان می‌دهد، تیم شروع به ignore کردن قرمزی‌ها می‌کند و باگ‌های واقعی از لای‌لای رد می‌شوند.
  5. ۵٪ از درخواست‌ها بیش از ۲ ثانیه طول می‌کشند (شاید حتی ۱۰ ثانیه!) — میانگین ۲۰۰ms این دُم سنگین توزیع را پنهان می‌کند؛ تجربه‌ی بد کاربران در صدک‌های بالا است.

فصل ۱۰ — معماری و اصول کدنویسی: زبان آرشیتکت‌ها

🎯 صحنه: جلسه معماری: «The monolith is fine for now, but let's at least decouple payments. Follow SOLID, avoid premature abstraction — KISS!» — واژه‌های طراحی نرم‌افزار که در code reviewهای معماری و مصاحبه‌های senior همه‌جاست.

۱۰.۱ — شکل سیستم: monolith تا microservices

اصطلاح یعنی جمله
monolith مونولیت — همه‌چیز در یک اپ «It's a monolith, and that's fine for now.»
microservices مایکروسرویس‌ها — سرویس‌های کوچک مستقل «Split payments into a microservice.»
decouple / coupling جداسازی / وابستگی «Payments and auth are tightly coupled.»
tightly coupled چسبیده به هم (تغییر یکی، می‌شکند دیگری) «This is tightly coupled to the DB schema.»
loosely coupled جداشده (سالم) «Aim for loosely coupled modules.»
modular ماجولار «Keep it modular — swap-in components.»
monorepo / polyrepo چند پروژه در یک ریپو / هر پروژه یک ریپو «UI and API live in a monorepo.»
serverless بدون سرور (توابع managed) «Auth goes serverless.»
event-driven رویدادمحور (کوئری و event) «The flow is event-driven via the queue.»
distributed system سیستم توزیع‌شده «Debugging distributed systems is hard.»
trade-off ترید-آف — معاوضه (این را بگیر، آن را بده) «Every architecture is a trade-off.»
over-engineering اِو-اِنجینیرینگ مهندسی بیش از حد

🔑 جمله‌ی کلاسیک آرشیتکت‌ها: «It depends.» — هر انتخاب معماری یک trade-off دارد؛ جواب مطلق وجود ندارد. و هشدار مشهور: premature optimization is the root of all evil (بهینه‌سازی زودهنگام ریشه همه شرارت‌ها — دونالد کنوث!).

۱۰.۲ — اصول کدنویسی (مخفف‌های مقدس)

اصل یعنی جمله
SOLID ۵ اصل طراحی شیءگرا (Single responsibility, Open-closed, Liskov, Interface segregation, Dependency inversion) «This violates the Single responsibility principle.»
DRY Don't Repeat Yourself — تکرار ممنوع «DRY it up — extract a helper.»
KISS Keep It Simple, Stupid — ساده نگه دار «KISS! Why the generic factory for one case?»
YAGNI You Ain't Gonna Need It — چیز الان‌لازم‌نشده نساز «YAGNI — we don't need 3 themes yet.»
Separation of Concerns (SoC) جداسازی دغدغه‌ها «Keep UI, logic and data separate.»
Single source of truth یک منبع حقیقت واحد «The config file is the single source of truth.»
readability > cleverness خوانایی بر هوشمندی «Don't be clever — be readable.»
clean code کد تمیز (کتاب رابرت مارتین) «Small functions, meaningful names.»

💡 SOLID باز شده (برای مصاحبه): Single responsibility = هر کلاس یک دلیل برای تغییر داشته باشد Open-closed = برای افزودن قابلیت باز، برای تغییر بسته Liskov substitution = زیرنوع باید جای نوع پدر بنشیند Interface segregation = interface های بزرگ پرچرب ممنوع Dependency inversion = به abstraction وابسته باش، نه پیاده‌سازی

۱۰.۳ — الگوها و ضدها

اصطلاح یعنی جمله
design pattern الگوی طراحی (راه‌حل استاندارد مسئله شناخته) «A factory pattern fits here.»
anti-pattern ضدالگو (راه‌حل رایجِ غلط) «God objects are an anti-pattern.»
singleton / factory / observer / strategy الگوهای کلاسیک «Use an observer for the events.»
god object / god class شیء خدا — همه‌چیز را می‌داند «UserService is a god class — 2000 lines!»
wrapper / adapter پوشاننده / مبدل «Write a thin wrapper over the SDK.»
abstraction انتزاع — پنهان‌کردن جزئیات «The abstraction is leaking!»
leaky abstraction انتزاع سوراخ (جزئیاتش پیدا می‌شود) «Classic leaky abstraction — the ORM exposes SQL.»
boilerplate بویلر-پلیت کد تکراری تشریفاتی
magic number / magic string عدد/رشته جادویی بی‌نام «What is 86400? Extract a constant!»
code smell بوِ کد (نشانه مشکل نه باگ) «Long parameter list is a code smell.»

🔑 code smell = چیزی که «بو می‌دهد» — کار می‌کند ولی نشانه طراحی ناسالم است (تابع ۵۰۰ خطی، کامنت‌های توضیح-دهنده‌ی کد بی‌معنی، conditional های تودرتو). بو → smell → بگرد، معمولاً یک refactor واقعی زیرش پنهان است.

۱۰.۴ — فرایند تصمیم معماری

اصطلاح یعنی جمله
POC (Proof of Concept) نمونه اثبات ایده «Build a POC first — one week.»
spike بررسی سریع بدون تعهد (در اسکرام) «Time-boxed spike on WebSockets.»
technical spec / RFC سند طراحی قبل از کد «Write an RFC and get feedback.»
benchmark بنچمارک — اندازه‌گیری مقایسه‌ای «Benchmark before you choose the ORM.»
greenfield / brownfield پروژه از صفر / پروژه موجود «Greenfield lets us pick the stack.»
migrate / migration path مهاجرت / مسیر مهاجرت «What's the migration path for users?»
vendor lock-in قفل‌شدن به یک فروشنده «Watch out for vendor lock-in.»
cutting corners کوتاه‌روی (کیفیت را فدا کردن) «We're cutting corners on security.»

✅ جمع‌بندی فصل

  • شکل: monolith تا microservices؛ decouple کن؛ همه‌چیز trade-off است؛ «It depends»
  • مخفف‌ها: SOLID/DRY/KISS/YAGNI — بازشده‌شان را برای مصاحبه بلد باش
  • الگو: design pattern ✅ / anti-pattern ❌؛ code smell یعنی «بو»؛ god object ممنوع
  • فرایند: POC/spike → RFC → benchmark؛ greenfield/brownfield؛ vendor lock-in

📝 تمرین فصل ۱۰

  1. درک: «We're over-engineering — a POC with no abstraction would answer the question in a day.» یعنی چی؟
  2. کدام اصل نقض شده؟ «تابعی که هم به دیتابیس وصل می‌شود، هم HTML می‌سازد، هم ایمیل می‌فرستد.»
  3. حالت‌سازی: lead می‌گوید «Rewrite everything in Rust.» تو با ۳ اصطلاح (trade-off، greenfield، premature) ریسک را بگو.
  4. YAGNI با یک مثال واقعی از پروژه‌هایت توضیح بده.
  5. کدام یک code smell است؟ (الف) تابع ۴۰۰ خطی با ۱۲ پارامتر (ب) تابع ۱۰ خطی با اسم معنادار (ج) کامنت توضیح الگوریتم پیچیده
جواب‌ها
  1. «داریم مهندسی‌بیش‌ازحد می‌کنیم — یک نمونه اثبات ایده بدون انتزاع، جواب سوال را در یک روز می‌دهد.»
  2. نقض Single responsibility (و Separation of Concerns) — سه دلیل تغییر متفاوت در یک تابع.
  3. نمونه: «That's a trade-off, not a free win — a rewrite is a greenfield project with real risk. We'd cut corners on features for months, and Rust expertise is a hiring constraint. Let's benchmark the bottleneck first — optimizing the wrong layer is premature.»
  4. مثال: ساخت سیستم theme switcher سه‌گانه وقتی هیچ مشتری ازش نخواسته (فقط «شاید بعداً»)؛ کد می‌میرد قبل از مصرف.
  5. (الف) — طول + پارامترهای زیاد = smell کلاسیک (Long method / Long parameter list).

  • چت: I'm on it / heads-up / PR is up / Blocked on X / Keep me posted
  • حرفه‌ای‌ترین‌ها: Good catch! / Sorry for the delay — was blocked on X / Mind reviewing?
  • ایمیل: Following up on... / As per our discussion / Apologies for the confusion

📝 تمرین فصل ۱۱

  1. این پیام لیدت را کامل ترجمه کن: «FYI the client moved the demo to Monday. TL;DR: we need the dashboard by EOD tomorrow. BTW can you CC me on the deploy notes? TIA!»
  2. کدام مخفف جای درست است؟ «___ we're sunsetting v1 — the docs are ___ outdated.» (TBD / FYI / e.g. / i.e.)
  3. حالت‌سازی: به چت تیمی بنویس که دیروز مسدود بودی روی طراحی، امروز شروع می‌کنی، و از دیزاینر درخواست ریویو مودبانه کن — با حداقل ۴ عبارت این فصل.
  4. فرق «e.g.» و «i.e.» در این دو جمله؟ (الف) «JS frameworks, i.e. React and Vue» (ب) «JS frameworks, e.g. React and Vue»
جواب‌ها
  1. «برای اطلاعت: مشتری دموی دوشنبه رو برد. خلاصه‌اش: داشبورد رو تا آخر فردا لازم داریم. راستی می‌شه توی یادداشت‌های دِپلوی من رو CC کنی؟ پیشاپیش ممنون!»
  2. «FYI we're sunsetting v1 — the docs are i.e. ✗ → درست: e.g. فقط اگر نمونه است؛ چون «docs outdated» توضیح همان موضوع است → i.e. درست‌تر: «FYI we're sunsetting v1, i.e. it stops working on Jan 1.» (اگر منظور نمونه باشد e.g.)
  3. نمونه: «Quick update: I was blocked on the design review yesterday — got the assets this morning, so I'm on it now. @Dana, mind taking a quick look at the header spec? Keep me posted if anything changes. 🙂»
  4. (الف) غلط — i.e. یعنی «همین‌ها هستند» ولی React و Vue نمونه‌اند نه همه؛ (ب) درست — «مثلاً React و Vue».

✅ جمع‌بندی فصل

  • آگهی: JD، remote/hybrid، must-have vs nice-to-have، «competitive salary» را جدی نگیر
  • سطوح: junior→mid→senior→lead؛ سطح = استقلال و اثر
  • فرایند: screening → take-home/live coding → system design → behavioral (با STAR)
  • بعدش: offer → negotiate → notice period → onboarding؛ سوال «success in 3 months?» را فراموش نکن

📝 تمرین فصل ۱۲

  1. این آگهی را رمزگشایی کن: «Senior dev for a fast-paced startup. You'll wear many hats. Competitive salary + equity.» سه واقعیت پنهان را حدس بزن.
  2. تفاوت «culture fit» و «culture add»؟ کدام را در مصاحبه بگویی؟
  3. یک جواب behavioral با STAR بنویس: «Tell me about a time you fixed a production bug under pressure.» (حتی به فارسی ساختارش را بچین)
  4. فرق hiring manager و recruiter؟ سوال فنی به کدام نپرسید؟
  5. offer گرفتی اما حقوق پایین است؛ جمله مذاکره حرفه‌ای را بنویس.
جواب‌ها
  1. حدس‌های معقول: فرایند رسمی کم و تغییر مکرر (fast-paced)؛ چند نقش باهم (wear many hats: شاید بک‌اند/دواپس هم)؛ حقوق پایه احتمالاً متوسط با وعده سهام (competitive+equity). سوال بپرس: نرخ turnover تیم؟
  2. culture fit = «مثل ما فکر می‌کند» (ریسک یکسان‌سازی)؛ culture add = «چیز جدیدی به تیم اضافه می‌کند». در مصاحبه بگو: «I think I'd be a culture add — I bring X experience the team doesn't have.»
  3. ساختار STAR (نمونه چینش): Situation = پنج‌شنبه شب ارور ۵۰۰ در چک‌اوت؛ Task = قبل از پیک خرید جمعه حل شود؛ Action = trace ID زدم، root cause یک migration اعمال‌نشده، feature flag خاموش، hotfix دیپلوی شد؛ Result = ۱۵ دقیقه تا رفع، postmortem نوشتم و migration gate اضافه شد که دیگر تکرار نشود.
  4. recruiter = فرایند استخدام و حقوق (اولین تماس)؛ hiring manager = سرپرست فنی آینده‌ات (تصمیم‌گیرنده). سوالات فنی عمیق را از hiring manager بپرس، نه recruiter.
  5. نمونه: «Thank you — I'm excited about the role! Based on my experience with X and the market range for this position, I was expecting something closer to Y. Is there flexibility on the base, or other parts of the package we could adjust?»
